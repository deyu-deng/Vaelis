# ADR-0011: 三级 Agent 架构与分层模型路由

- **状态**：Accepted
- **日期**：2026-08-24
- **决策者**：MVP-AI-Secretary-Requirements V0.3（决策⑩）
- **关联**：ADR-0006（底座与编排）、`vaelis/north_star/GRILL_FREEZE.md`（术语升级）、`specs/agenda-board.md`

## 上下文与背景

北极星契约此前用「Master + Marvis HID」描述算力分工，且冷启动模型定为 DeepSeek。需求进一步明确为**三级 Agent 体系**，同时一级要用市面最好模型（当前 Kimi K3），这带来两个必须处理的约束：

**成本约束（核实数据）**：Kimi K3 国内区计价为输入 ¥20/M（缓存未命中）、¥2/M（命中）、**输出 ¥100/M**，1M 上下文；且 K3 **始终开启思考，推理 token 计入输出**。官方另提示：多轮工具循环必须原样回传上一轮完整 assistant message（含 `reasoning_content`），且不应在推理链中途切换模型。

粗算单轮（约 10k 输入多数命中 + 1.5k 输出）≈ ¥0.17，缓存未命中约 ¥0.35。若一级模型承担逐条消息分类，日均 50 轮将达 ¥250–500/月；若只承担统筹与对话，日均 10–20 轮约 ¥50–100/月。用户当前无项目收入，生活费约 ¥1800/月，故成本纪律必须写进架构而非留作实现细节。

**硬件约束**：Pico 2W 仅一只，多个 Agent 并发驱动 GUI 会争抢前台。现有 `plugins/vaelis-north-star/lib/hid/device.py` 的 `ScreenLock` 只是 30 秒忙等互斥锁，无队列、无优先级、无公平性，多 worker 场景会互相饿死。

## 决策

### 1. 三级 Agent 架构

| 层 | 角色 | 模型/算力 | 职责边界 |
|---|---|---|---|
| **L1** | 常驻秘书，用户直接对话，与 Mind 深度结合 | 市面最好（当前 Kimi K3） | 只做统筹、决策、派工、与用户对话 |
| **L2** | 每个项目/专职任务一个，有记忆 | 便宜模型或 aigw 聚合额度 | 领域任务闭环；调用模型做分类/抽取/执行 |
| **L3** | 专能子 Agent + GUI 闭源软件执行体 | 尽量零 token（GUI / Pico HID） | 承接额度无法转为 API 的闭源软件工作 |

术语升级：北极星契约中的「Master」= L1；「Marvis」原为类比，现指 L2 级项目 Agent（不特指某软件）。

### 2. 分层模型路由与成本纪律

- 配置层提供 **角色 → 模型** 路由；L1 与 L2 必须使用不同模型且均可配置。
- **L1 不参与**逐条消息分类、抽取与工具循环；只接收摘要。此为预算硬约束，非架构审美。
- 规划任务（里程碑 M2）若成本偏高，可下放专职 L2「规划员」。因规划在状态结构化后主要是机械操作（读次日事件 → 查冲突 → 排序 → 附证据），质量取决于 SQLite 字段与 Mind 偏好画像的质量，而非模型智商。
- L1 与 L2 使用**独立会话**，不在同一条消息历史中切换模型（遵循 K3 官方提示）。

### 3. Mind 读写口

- **L2 直接读**自己项目子树（读无并发问题，也避免让 L1 转述而付出 ¥100/M 的输出成本）。
- **写入统一经一个不带 LLM 的 Mind 写入服务**：串行队列 + 安全前缀校验 + 批量提交 + 提交前跑 `verifier.py` 预检。
- 由此把"串行化成本"从 L1 的 token 降到守护进程的 CPU，同时避免多 L2 并发写 git 仓库触发 verifier BLOCKER。

### 4. Pico 单设备排队

- 采用**优先级队列**：前台交互 > 时效任务 > 夜间批量；同级 FIFO；带单任务时间片上限（超时释放并重排），用户手动交互可抢占。
- 归属最终形态，**里程碑 M3 实现**；M1 无 L3 实例，不实现队列（当时无消费者）。

### 5. MVP 阶段的实例化

M1 只有两个真实角色：L1（用户偶尔对话的秘书）+ L2「日程秘书」（常驻，负责采集→分类→维护 SQLite→推钉钉）。即便如此也先建立 L1/L2 分离与角色→模型路由，避免模型选择硬编码在采集脚本里。

## 考虑过的选项

| 选项 | 说明 | 否决/采纳理由 |
|------|------|--------------|
| L1 严格限流（只统筹与对话） | 分类/抽取/工具循环下放 L2 | 采纳：约 ¥50–100/月可持续，且"最好模型"用在判断力上 |
| L1 全程参与（含消息确认） | 体验一致 | 否决：¥250–500/月，占生活费 14–28%，不可持续 |
| 先用便宜模型，K3 待有收入再上 | 全程低成本 | 否决：感受不到旗舰模型差别，等于放弃该决策的意义 |
| L2 写 Mind 经 L1 转述 | 保住 Mind 单写入口 | 否决：让 ¥100/M 输出的模型干搬砖活，成本不合理 |
| L2 各自直接写 Mind | 最省 token | 否决为最终形态：多写入方并发 git 提交 + verifier 必然冲突 |
| L2 直读 + 无模型串行写入服务 | 兼顾成本与一致性 | 采纳 |
| Pico 简单互斥 + 重试（现状） | 无需新增机制 | 否决：无优先级会让夜间批量堵住时效任务，违反 15 分钟 SLA |
| Pico 纯 FIFO 队列 | 实现简单、公平 | 否决：同上，紧迫度差一个数量级的任务不应同队 |

## 后果

### 正面影响

- 一级模型的高成本被限制在高价值场景，月度支出进入可持续区间。
- 职责分层清晰：L1 统筹、L2 领域闭环、L3 零 token 执行，与「Master 窄接口」原则一致。
- Mind 写入串行化后，多 Agent 场景不再触发 verifier BLOCKER。
- Pico 排队策略与既有的时效性 SLA、夜间自治语义对齐。

### 负面影响与代价

- 需要维护角色→模型路由配置与预算监控，否则成本纪律只是文档。
- L1/L2 会话分离意味着上下文需要显式摘要传递，实现比单会话复杂。
- Mind 写入服务是新增常驻组件，需自身的健康检查与失败重试。
- Pico 优先级队列推迟到 M3，期间若临时需要 GUI 驱动只能串行手工协调。
- K3 要求回传完整推理历史，长工具循环会让上下文与账单同步膨胀——这进一步要求 L1 远离工具循环，需在实现中强制。
