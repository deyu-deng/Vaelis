# ADR-0009: 消息触发的日程变更采用「待确认 + 钉钉双向确认」

- **状态**：Accepted
- **日期**：2026-08-24
- **决策者**：MVP-AI-Secretary-Requirements V0.3（决策⑧）
- **关联**：ADR-0002（通知通道）、ADR-0005（规则+模型识别）、`specs/agenda-board.md`

## 上下文与背景

采集层识别到「明天的会改到下午三点」这类消息后，系统面临一个语义选择：直接改日程，还是等用户点头？

约束条件有三：

1. 北极星契约冻结了「**人只负责审核和提想法**」。
2. 识别链路是「规则过滤 + 模型确认」（ADR-0005），模型存在幻觉与误判风险；静默改错日程的代价高于漏改。
3. MVP 成功标准需要一个**可测量**的质量指标，而原「计划吻合率 ≥ 80%」缺少 ground truth 采集口。

同时，通知侧原方案为钉钉自定义机器人 webhook，而**自定义机器人 webhook 是单向的**，只能推送、无法接收用户回复，不足以承载确认动作。

## 决策

**消息触发的日程变更一律写入 `pending`（待确认），由用户确认后才落定；确认通道为钉钉 Stream 模式机器人（双向）。**

- 状态机：`pending` --确认--> `confirmed`；`pending` --忽略--> 回滚到 `prev_value`（若为新建项则删除）。
- 看板呈现：`pending` 条目带徽标并显示新旧值对比与证据片段。
- 手动录入例外：`source=manual` 直接为 `confirmed`（用户手输即事实）。
- 钉钉协议：推送带当日递增短序号，用户回复 `确认 N` / `忽略 N`；序号 **24 小时**有效；无法解析的回复不做猜测，回用法提示。
- 通道形态：使用钉钉 **Stream 模式**机器人（仓库 `plugins/platforms/dingtalk/` 已有入站适配），而非仅出站的自定义机器人 webhook。
- 副产品：确认/忽略动作即质量数据，MVP 成功标准改为「用户手动删除或修改的条目比例 ≤ 20%」，无需额外反馈机制。

## 考虑过的选项

| 选项 | 说明 | 否决/采纳理由 |
|------|------|--------------|
| 待确认 + 一键确认 | 标 pending，人点头才落定 | 采纳：契合「人只审核」；确认动作零额外负担且自带 ground truth |
| 自动改 + 事后通知 | 直接更新，推「已改期」 | 否决：模型判错时静默产生错误日程，用户看到的是假事实 |
| 按置信度混合（高置信自动、低置信待确认） | 分档处理 | 否决（暂缓）：早期没有标注数据无法校准阈值；待「待确认」跑一两周积累标注后再升级 |
| 钉钉交互卡片 + 回调按钮 | 消息内直接给按钮 | 否决（暂缓）：体验更好但需卡片模板与回调可达性（公网/穿透），工作量显著更高 |
| 仅推送、确认回桌面看板 | 钉钉只做通知 | 否决：用户离桌时无法落定，实时通知的价值减半 |

## 后果

### 正面影响

- 错误识别不会污染日程真源，用户始终看到经自己认可的事实。
- 手机一句话即可落定，离桌场景可用。
- 质量指标自然采集，验收从"不可测"变为"可测"。

### 负面影响与代价

- 用户每次变更都需要一个确认动作；若误报率高会变成骚扰，需靠白名单（ADR-0010）与规则调优压低噪音。
- 引入 `pending` 状态与 `prev_value` 回滚逻辑，状态机比"直接改"复杂。
- 依赖钉钉 Stream 模式常驻连接，连接中断期间确认不可用（需要健康检查与告警）。
