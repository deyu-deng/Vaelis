# ADR-0002: MVP 通知通道采用钉钉机器人过渡

- **状态**：Accepted（2026-08-24 修订，见文末「修订记录」）
- **日期**：2026-08-24
- **决策者**：MVP-AI-Secretary-Requirements V0.2（决策①）、V0.3（决策①修订）

## 上下文与背景

Vaelis MVP 需对时效性消息（会议改期、DDL 变更）实时通知用户（成功标准：15 分钟内识别并通知）。
通知通道的选择受限于 MVP 阶段投入与正式版形态差异：正式版规划为桌面端原生计划看板 +
原生通知机制，并最终适配各系统独立 Vaelis 移动端；MVP 阶段不应过早投入原生端建设。

## 决策

**MVP 阶段通知通道采用钉钉机器人通知过渡**；正式版为桌面端原生计划看板 + 原生通知机制；
后续适配各系统独立 Vaelis 移动端。通知层需做抽象，保证通道可切换。

来源：MVP-AI-Secretary-Requirements.md §5 决策①、§2.1。

## 考虑过的选项

| 选项 | 说明 | 否决/采纳理由 |
|------|------|--------------|
| 钉钉机器人 | 基于既有钉钉使用环境，零新增客户端，推送可达 | 采纳为 MVP 过渡方案 |
| 桌面端原生看板+原生通知 | 正式版目标形态 | MVP 阶段建设成本高，推迟至正式版 |
| 微信通知 | 微信通道对自动化推送限制较多 | 否决：通道稳定性与合规性不如钉钉机器人 |
| 独立移动端 | 最终形态 | 否决：MVP 阶段不投入移动端建设 |

## 后果

### 正面影响

- 通知通道即刻可用，支撑 MVP 时效性消息通知验收。
- 通知层抽象保留，后续切换正式版通道成本低。

### 负面影响与代价

- 钉钉机器人依赖用户钉钉使用环境，若学校/组织策略变化可能失效。
- 过渡方案与正式版形态不一致，需在正式版阶段完成通道切换。

## 修订记录（2026-08-24，MVP V0.3）

1. **机器人形态收敛为 Stream 模式（双向）**。原方案未区分形态；而 ADR-0009 的「待确认 + 一键确认」要求用户能回复，**自定义机器人 webhook 是单向的、收不到回复**。因此改用钉钉 Stream 模式机器人（仓库 `plugins/platforms/dingtalk/` 已有入站适配），用户以文本 `确认 N` / `忽略 N` 落定变更。
2. **「桌面原生看板」不再是正式版专属**。ADR-0008 将内置日程看板提前进入 MVP，与钉钉机器人并存：看板负责在桌全景与手动编辑，钉钉负责离桌通知与确认。本 ADR 中"正式版为桌面端原生计划看板"的范围划分以 ADR-0008 为准。
3. 未变更的部分：通知层保持抽象、通道可切换；最终形态仍是独立 Vaelis 移动端。
