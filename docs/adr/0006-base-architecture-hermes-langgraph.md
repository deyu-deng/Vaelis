# ADR-0006: 底座架构维持 Hermes 不迁移、逐步引入 LangGraph 编排

- **状态**：Accepted（2026-08-24 修订，见文末「修订记录」）
- **日期**：2026-08-24
- **决策者**：底座调研结论（非 MVP 需求文档记载，依据为底座调研）；MVP V0.3（决策⑤）补充生效条件

## 上下文与背景

Vaelis MVP 采用"主秘书 Vaelis + 多个有记忆的 Marvis + 共享资源池"分层架构。
底座调研评估了现有 Hermes 编排组件与 LangGraph 编排方案：Hermes 为既有运行组件，
迁移风险高；LangGraph 提供更成熟的图编排能力。需确定底座演进路线，
避免在 MVP 阶段承担不必要的迁移风险。

## 决策

**底座架构决策：Hermes 不迁移，逐步换 LangGraph 编排**——MVP 阶段维持 Hermes 现状，
不执行迁移；后续按需分步将编排逻辑过渡到 LangGraph，边验证边替换，避免大爆炸式迁移。

依据来源：底座调研结论（Hermes 评估、LangGraph 评估）。本决策未在
MVP-AI-Secretary-Requirements V0.2 中记载，属于调研层面的架构方向，非 MVP 验收项。

## 考虑过的选项

| 选项 | 说明 | 否决/采纳理由 |
|------|------|--------------|
| Hermes 不迁移、逐步换 LangGraph | 维持现状，按需渐进替换编排 | 采纳：迁移风险低，MVP 不阻塞 |
| 立即迁移到 LangGraph | MVP 阶段即完成编排替换 | 否决：迁移风险高，MVP 时间窗内不值得 |
| 继续使用 Hermes 不换 | 永久维持 Hermes | 否决：编排能力演进受限，失去 LangGraph 优势 |

## 后果

### 正面影响

- MVP 阶段规避迁移风险，聚焦业务闭环验收。
- 渐进式替换保留未来编排能力升级路径。

### 负面影响与代价

- 过渡期 Hermes 与 LangGraph 可能并存，需维护两套编排边界。
- 换编排为长期演进项，需在后续迭代规划中持续跟踪。

## 修订记录（2026-08-24，MVP V0.3）

**MVP 阶段明确不引入 LangGraph。** 现状核实：仓库 `pyproject.toml`、`aigw/pyproject.toml` 与全部 Python 代码中 **零 langgraph 依赖、零 import**，本 ADR 此前的"逐步引入"仅为方向表述，无落地。

MVP（里程碑 M1）的编排实际形态是「定时触发 + 本地规则过滤 + 单次模型调用」，用不上图编排；此时引入既违反复用调研纪律（`north_star/OSS_REUSE.md` 的 O3：动手前须有复用调研），也会把 L1 变重（违反 Master 窄接口原则）。

**引入的触发条件**（满足其一再启动调研与切片）：

- 出现真实的多分支 / 循环编排需求，用现有委派机制表达明显笨拙；
- 出现需要持久化、可恢复的人在环状态机（例如里程碑 M3 的执行—验证—回报闭环跨进程重启）；
- 出现多 L2 Agent 协同且需要显式图状调度的场景。

在此之前，编排保持现状，本 ADR 的方向性结论不变。
