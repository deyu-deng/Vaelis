## 一、红线检查方法（验收硬闸门）

> 以下四条红线为产品级"绝对不能接受"项，任何功能交付必须通过，否则视为未达标。

| 红线 | 要求 | 通用检查方法 |
|------|------|--------------|
| 红线 1 | 任何 Loading 超过 300ms 必须有进度提示 | 逐屏检查所有异步加载入口：读取、SSE 连接、列表首载、卡片状态过渡，确认均有加载指示或骨架屏 |
| 红线 2 | 对话延迟超过 50ms 才开始显示第一个字符 | 建立可重复性能基准，测量 `send → first_token_rendered` 端到端延迟；无即时反馈时需"思考中"脉冲指示 |
| 红线 3 | 双击 Agent 卡片进入 Focus Mode 不得有明显卡顿 | 使用 Playwright / DevTools Performance 实测交互延迟与帧率；大列表需懒加载 |
| 红线 4 | 预览区在成品完成前不得完全空白 | 生成中需占位 UI 或进度指示；评估流式预览（如 AG-UI STATE_DELTA） |

## 二、验收方法（如何证明"达标"而非"文件存在"）

核心教训：**代码存在 ≠ 功能可靠**。每条功能需以下任一方式背书后方算交付：

- **端到端测试**：覆盖 `用户发消息 → 首字渲染` 及 `plan.md 生成 → 分配 → 聚合` 闭环
- **性能基准**：红线 2 的 `<50ms` 首字延迟须有可重复基准测试
- **断言验证**：搜索结果质量、标题质量等须有断言，而非"调用即完成"
- **术语合规扫描**：CI 中扫描禁别名（如"子 Agent"），违规即失败

## 三、非功能需求（NF-1 ~ NF-9）

## 四、技术约束（不重复造轮子）

1. 编排层保留 LangGraph（挂 checkpointer 支持流式与中断恢复）
2. 前端协议优先 AG-UI（替换 hand-rolled SSE），直接对应红线 2、4
3. 工具调用用 `bind_tools` + LangGraph `ToolNode` 建立真实工具回路
4. 工具/集成优先官方 MCP servers；多 SaaS 按需用 Composio（慎用）
5. 记忆用 mem0 或 LangGraph checkpointer，替换 KV 注入
6. 重活以外部专家 Agent（OpenHands / browser-use）经 A2A 委派，**禁止 fork 大仓**
7. 测试用 LangChain 假模型 + pytest-asyncio 实现确定性 e2e，不依赖 API key
